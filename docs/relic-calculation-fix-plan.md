## 1. 审计口径

当前数据库共有 1797 件藏品，其中 802 件具有 active 计算规则，共 1024 条 active 规则：394 条为 `approved`，630 条仍为 `pending`。

### 1.1 产品计算边界

本项目只关心以下结果：

- 我方干员面板：生命、攻击、防御、法术抗性、攻击速度等已经进入面板模型的属性。
- 敌方面板：生命、攻击、防御、法术抗性、攻击速度等已经进入敌人面板模型的属性。
- 最终单次伤害：物理、法术、真实伤害类型，伤害倍率、无视防御等直接影响当前命中结果的属性。

以下效果明确不纳入计算，也不为它们扩展模型：

- 技力、技力回复、初始技力和技能循环。
- 部署费用、费用返还、费用上限和再部署时间。
- 阻挡数、闪避、抵抗、控制、束缚、晕眩等战场机制。
- 招募、希望、源石锭、目标生命、节点、关卡奖励等局外效果。
- 部署时、敌人进入保护点时、每隔若干秒等事件触发的独立伤害。
- 对队友提供但不改变当前计算对象面板或当前单次伤害的效果。

处理原则：一件藏品可以只实现其中直接影响面板或最终伤害的部分；未建模部分应在 `note` 或 `ignored_reason` 中说明，但不能误解析为其他面板属性。若藏品没有任何处于产品边界内的效果，整件规则应标记为 `ignored`。

本文把项目分成两类：

- **已确认错误**：由描述、数据库规则和实际运行结果三方交叉验证，可以直接进入修复。
- **需要逐项复核**：规则缺少适用对象或运行条件，当前实现会无条件生效；修复前仍需确认产品模型是否准备支持描述中的全部效果。

验收原则：

1. 当前干员不满足职业、部署位置或分支职业时，限定效果必须为 0。
2. 多个适用对象具有不同数值时，不得把数值相加后挂在单个 `applies` 上。
3. 敌人面板效果只能进入 `enemy_panel`，干员面板效果只能进入 `operator_panel`。
4. “额外造成一次真实伤害”不得把普通攻击的伤害类型改成真实伤害。
5. 首次攻击、持续时间、关卡、范围、数量、随机目标等条件必须显式建模；模型暂不支持时应标记 `ignored`，不能无条件近似。
6. 技力、部署费用等边界外效果不要求实现，但必须保证它们不会污染敌我面板或最终单次伤害。

## 2. 项目中的正确自动判断链路

项目已经支持 `profession`、`position`、`sub_profession_cn_any` 三种自动条件。前端选择干员时写入 `applies`，后端在请求未提供该值时再次自动判断。

因此修复职业类藏品时应复用现有 `auto_rule`，而不是另写一套职业判断。相关位置：

- 后端自动匹配：`backend/app/combat/relics.py::match_applies_auto`
- 后端参数解析：`backend/app/combat/relics.py::_resolve_param_values`
- 前端自动匹配：`frontend/src/pages/PanelPage.tsx::matchAppliesAuto`
- 条件入库：`relic_condition_params.auto_rule`

当前有 186 件藏品使用自动条件；问题主要是覆盖不完整和部分规则拆分错误。

## 6. 数据库与代码改造方案

### 6.1 短期方案

1. 为标准单职业规则补齐 `relic_condition_params(auto_rule)`。
2. 删除所有错误的 `true_damage=1` 事件型规则。

## 追加修复：敌人类型、叠层与元素伤害

| 藏品 | 原问题 | 修复方案 |
|---|---|---|
| 探测先锋 | 错误强化干员，且无敌人类型与层数选择 | 增加“当前敌人为猎犬proto”开关和追猎层数；每层仅令该敌人 HP、ATK +20% |
| 厄运火杆 | 居民限定和永久攻速叠层均被当作常驻 | 增加“当前敌人为居民”开关与胜利层数；居民 HP -40%，每层干员 ASPD +10 |
| 犬植浆 | 固定按一层计算 | 增加覆盖当前干员的层数；每层 ATK +10% |
| “阿猛” | 错误增加所有最终伤害 | 增加元素伤害类型和元素受伤加深；仅元素伤害 ×200% |

| 猎印 | 把猎犬 proto 攻击 -50% 错误施加给干员，且遗漏探测先锋层数法抗 | 增加猎犬 proto 开关和探测先锋层数；敌人 ATK -50%，当前干员每层 RES +10 |
3. 修正敌人/干员目标写反的规则。
4. 对当前模型无法表达的效果改成 `calculation_status='ignored'`，填写明确 `ignored_reason`。
5. 所有修正规则写成 `source='manual'`、`review_status='approved'`，避免同步时再次被解析结果覆盖。

### 6.2 中期结构改造

当前条件挂在藏品级参数上，一个 `applies` 很难表达“特种 +30%、术师 +3%”。建议让每条 `relic_effect_rules` 可以引用不同的自动适用条件：

- 方案 A：给规则增加 `auto_rule JSON`。
- 方案 B：增加 `relic_rule_conditions` 子表，一条规则可有多组 AND/OR 条件。

优先建议方案 B，后续可统一表达职业、分支、位置、敌人类型、关卡、持续时间和状态条件。

## 7. 验证计划

每件修复藏品至少增加以下测试：

1. 满足条件的干员得到描述中的精确数值。
2. 不满足条件的干员对应效果为 0。
3. 敌人规则不会改变干员面板，干员规则不会改变敌人面板。
4. 条件关闭和开启的差值等于描述值，而不只检查正负号。
5. 同名藏品的不同主题 ID 分别测试，防止只修一个副本。
6. 通过真实 `/api/v1/calc/panel` 请求验证 `final_panel`、`enemy_final_panel`、`relic_contributions` 和 `hit_damage`。

完成规则修复后，应重新生成全量审计报告，并将通过标准从“方向正确”升级为“目标、精确数值、条件、伤害类型全部一致”。
